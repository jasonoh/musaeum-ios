# Slice 4's evidence

Two things live here: the **frames from the live probe** of 2026-09-23/24 — the simulator against a real Musaeum on slice 1's isolated profile (8 EPUBs, plus the five books these runs added) at `http://100.125.135.108:8789`, iPhone 17 Pro / iOS 26.1 — and the **campaign** the slice's unit deciders were put through on 2026-09-24. They are committed because the probe profile is throwaway and a measurement that lives only in a session is not a decider. The numbers beside each frame are in *Built — slice 4* of `docs/specs/2026-09-22-client-v1-design.md`; the command that reproduces each run, with the `MUSAEUM_PROBE_*` variable it needs, is `scripts/live-probe.sh`'s header.

**One gap, recorded first because a later session would otherwise read it as a missing run: the probe runs' own log lines were not captured to files.** The frames are what the session kept, and the app's `upload …` lines lived in a terminal that is gone. What is *not* gone is the library the runs wrote to, and its own record is quoted under each frame — a book that landed is a row the Mac created, and the runs that were refused left no row at all. So the frames and the library together decide these readings; a bare frame on its own would not.

Two things about this profile the next session needs. The port is **8789, not 8788** — the owner's own packaged Musaeum held 8788 for the whole of this slice's work, and it was never touched or signalled. And the profile's library **grew by five books** across these runs, which is what makes the rows below the evidence rather than a souvenir: three from the phone, two from `api-smoke.sh`.

## The campaign

`slice4-campaign.json` (15 rows) — run by `mutation-campaign.py` from the `musaeum-slice-workflow` skill, with this directory's `focused-test.sh` as the runner, one focused suite per row, and the raw per-run output in `slice4-runs.log` beside the verdicts in `slice4-campaign.log`. Each row's anchor was asserted to match its file **exactly once** before the campaign ran, and every row reports `restored=True`; the tree was checked for a stray mutant afterwards as well, because the restore is a loop's tail and a `kill` skips it (3b's trap 4 — which this campaign then paid for too, see below).

**13/15 killed, every file restored (`restored=True` on all fifteen rows), and the tree checked afterwards for a stray mutant.** Two caveats a reader needs before quoting any of it. A row's runner number is an **assertion** count, not a count of cases — 3b's trap — so the names in the last column are the evidence and the counts are not; and several rows reddened more than one case (the claims row five, the two format rows two, the sweep row three), of which the table names the case the campaign log reports, with every failing case in `slice4-runs.log` beside it. The campaign was **run twice**: its first run aimed the retryability row at `UploadTests`, where it survived, and the suite that decides it is `ClientTests` — a survivor can be the campaign's aim rather than the suite's gap, which is why the row was re-aimed and re-run rather than reported as found.

**Two traps this campaign paid for, both already in 3b's record and both met again here.** `xcodebuild test` stages a simulator sysdiagnose of about ten minutes on a failing row unless `-collect-test-diagnostics never` is passed — a row sat with no verdict line long enough to look like a hung build before the flag went into `focused-test.sh`. And killing a campaign mid-row leaves its mutant in the tree, because the restore is the loop's tail: it happened here **twice**, both times reversed by reading `git diff`, restoring the file, and re-checking every anchor before restarting.
